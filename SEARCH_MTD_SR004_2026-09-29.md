Inspection established these dependencies directly from current source:

  `beginRequest/endRequest`, advances one TT generation, and publishes only
  completed iterations. The research adapter runs under this unchanged driver.
- Public `ExactSearch.searchWindow` accepts root windows within +/-32769 and
  uses the same fail-soft PVS recursion as full-window calls. TT-off remains
  ordered alpha-beta. Root narrow calls need no change to PVS.
- Search scores are ordered integers in [-32768,32768]. Ordinary scores occupy
  [-32511,32511]; mate bands begin at +/-32512 and use actual root/path ply,
  with the existing add/subtract-ply TT normalization. +/-32769 are threshold
  infinities; `Value.INVALID` is not a score. Arithmetic across the ordinary/mate
  boundary requires no discontinuity or centipawn conversion.
- Score evidence requires the unchanged history/status-sensitive `SearchKey`,
  equal remaining depth and current generation. EXACT may return; LOWER/UPPER
  only cut when they prove the caller's cutoff, without non-cutting tightening.
  Hash moves remain legally validated ordering hints; accepted writes alone
  replace them. Same-key writes with `depth <= existingDepth` and
  `type >= existingType` are rejected, even when a new same-type bound is
  numerically stronger. This experiment leaves that rule untouched.
- Positive-depth root results must include a legal move unless terminal.
  Narrow results can carry bound prefixes; full/interior exact results permit
  TT-truncated exact PV prefixes. A narrow bound PV is not published as exact.
- Quiet history resets at every fixed-depth invocation, including each MTD
  pass and materialization. This cost and loss of invocation-local history
  are part of the architecture measured here.

## Convergence and completed-result proof

CONTROL invokes full-window ExactSearch once per depth. MTD-PREV uses the
previous fully completed score as a guess after full-window depth 1.
MTD-ORACLE uses the matching CONTROL score, transferred only as an integer;
CONTROL never lends its table or Search owner. All three start each request
with fresh independent default TTs (64 MiB requested, 2,097,152 slots / 48 MiB
logical storage). Within each request the same table and generation persist.

Initialize proven bounds `L=-32768, U=32768` independently of the guess `g`.
While `L<U`, select `beta = (g==L ? g+1 : g)` and search `[beta-1,beta]`.
The driver asserts `L<beta<=U`. No integer Search score is strictly inside.
A completed score `s>=beta` proves `L=max(L,s)`; otherwise `s<=beta-1` proves
`U=min(U,s)`. Reject contradiction or failure to shrink. Each pass strictly
shrinks a finite interval and stops only at `L=U=V`. Helpers reject scores
outside the valid domain before adjacent-threshold arithmetic, including
infinities, invalid sentinel and integer extrema.

Always materialize with the smallest integer window strictly containing V,
`[V-1,V+1]`, in the same TT generation. Require a completed interior result
equal to V. Existing cutoff-only root bounds cannot resolve that wider window
unless they are already EXACT. No bound classification is changed and no PV
is reconstructed from arbitrary hash moves. All materialization work is counted.

A stop during any zero pass or materialization leaves the target depth
incomplete, with no score, move or PV. Exhaustion between passes, including
after bound convergence, also leaves it incomplete. The unchanged driver
retains only the prior exact iteration. An exact final admitted child may
unwind successfully, preserving the existing node-budget convention.

## Empirical method and reproducibility

Windows 11, AMD Ryzen 5 5500 (6 cores / 12 logical processors), OpenJDK 21;
Search is deterministic single-thread HCE. JVM flags match SR-006 conventions:
`-Xms512m -Xmx2g -Xbatch -Djava.awt.headless=true`.

Reuse all 33 unique SR-006 FENs drawn from the ordering suite, ExactSearch
fixtures, SearchBenchmark corpus and DefaultPerftPositionLibrary. All request
depth 6; eight request depth 8: start, Kiwipete, tactical, evasion, middlegame,
transposition-pawns, endgame, quiet-endgame. Terminal mate/stalemate correctly
complete at depth 1. The suite includes promotions/underpromotions, checks,
castling, en passant, tactical and quiet endings, and both winning/losing mates.
Exact FENs and fixture provenance are in `positions.csv`.

Complete correctness/diagnostic runs first. Then two warmup rounds over the
eight deeper fixtures at depth 5 for all strategies. Three clean repetitions
rotate strategy order by position and repetition, using fresh ownership every
time. TT allocation, fixture construction, file output, CONTROL-oracle score
acquisition and PV validation are outside timed requests. The free perfect
guess is intentionally diagnostic and is not an implementable production cost
model. Request times include driver/observer/pass-record overhead; each pass
includes normal root generation, entry/reset, Search and result conversion.

Primary nodes count admitted children, matching SearchDriver/SR-006: PVS
re-entry is not another child admission. Raw `visited_nodes` additionally count
all recursive invocations including roots and PVS re-entry. No work from MTD
passes or final materialization is omitted. TT counters exist only in the
separate diagnostic subclass, never clean timing runs.

## Guesses, pass sequences and reuse

Distributions count the 171 distinct nonterminal depth>=2 targets once.
PREV uses 4,073 zero-window passes (12,219 across timing repetitions), mean
23.82, median 6, maximum 342. ORACLE uses exactly two passes for every target:
342 distinct passes, or 1,026 across repetitions, always fail-high then fail-low.
PREV has 2,679 fail-lows and 1,394 fail-highs. Each sequence is monotone in its
search direction until the final opposite result proves convergence.

Signed guess error is `initialGuess - exactScore`, in Search units.
PREV mean signed error +32.29; median absolute error 68, mean 550.13,
maximum 31,652; 15 guesses are exact. Those large raw errors include discovering
mates and are not centipawn errors. Restricting to 161 ordinary-to-ordinary
targets gives mean absolute error 193.60, median 77, maximum 1,212.
ORACLE's errors are all zero.

Largest pass counts include endgame d8: 342 (guess error +519), start d8:
334 (+338), start d7: 272 (-302), middlegame d8: 234 (+367).
Mate discovery can make a large fail-soft jump: forced-loss d4 bridges a
31,652-unit error in 12 passes and double-check d5 bridges 31,251 in five.

Example start d8 PREV: first `[203,204]` returns UPPER 203 in 406,553 nodes;
second `[202,203]` returns UPPER 202 in just 226 nodes; third needs 781.
However the long tightening sequence subsequently grows expensive: pass 333
returns UPPER -134 in 232,654 nodes; pass 334 `[-135,-134]` proves LOWER -134
in 139,495 nodes; `[-135,-133]` materializes in 274,616 nodes.
Per-pass CSV preserves every threshold, fail-soft score, interval, node/time
sample in order, including this 334-pass staircase.

In the separate diagnostic run, the first two passes above have respectively
35,107/221,111 and 209/218 mechanical TT hits/probes. The second pass makes
30 save attempts: the current equal-depth reuse can eliminate much repeated
work, as the focused generation/root-bound test independently establishes.
But later passes are not uniformly cheaper. PREV's adjacent pass transitions
are cheaper 1,062 times, dearer 2,779 times, equal 61 times. ORACLE's second
pass is cheaper only 33/171 times, dearer 137, equal once; it often has to
prove the more expensive opposite side of the exact value.

Total diagnostic hits/probes: CONTROL 824,984/4,279,864;
PREV 21,955,086/29,656,270; ORACLE 718,920/3,757,532. These are matching-key
mechanical hits, not claims that every hit has applicable depth or cuts off.
`diagnostic_passes.csv` separates EXACT/LOWER/UPPER hits and save attempts.
There is no production statistics change, no accepted-write counter and no
TT-cleared counterfactual; the causal contribution of each retained entry is
not independently quantified.

The existing single-slot same-key rejection rule means successive stronger
same-type bounds need not replace older evidence. Quiet history also resets
on every pass. Both are verified conditions of this result, not newly proposed
policy changes; this unit does not isolate either as the cause of the staircase.

## Materialization and entry cost

PREV materialization totals **1,411,587 nodes / 0.7341 s**, 0.938% of its nodes
and 0.943% of time. ORACLE totals **37,308 nodes / 0.01775 s**, 0.099% / 0.078%.
The perfect-guess savings survive exact-result recovery. PREV's materialization
can be substantial on an individual last depth, but its aggregate regression
is overwhelmingly convergence work.

For start d8 ORACLE, the first two passes take 722,018 and 206,768 nodes,
followed by only 226 materialization nodes. The retained bound proofs are
useful even though zero-window root calls cannot themselves publish exact PVs.

Aggregate throughput is +17.8% for PREV and +0.6% for ORACLE relative to
CONTROL. Summed request minus pass time is about 0.086 / 0.019 / 0.009 s for
CONTROL / PREV / ORACLE; these small residuals include observer/driver/record
work and timer noise. Entry/reset work *inside* every pass is already timed
but not separately instrumented. The data does not support repeated entry/JVM
overhead as the primary explanation for PREV's regression: it visits far more
nodes while sustaining higher admitted-node throughput. Throughput differences
also reflect tree shape and TT-hit mix, so this is not an isolated entry-cost
measurement or a universal per-node speed claim.

## Evidence and reconciliation boundary

`SEARCH_MTD_SR004_2026-09-29_EVIDENCE.zip` contains configuration, exact FEN

The observed architecture can support a correct repeated zero-window driver
and cheap exact-result materialization without changing recursive Search.
Perfect guesses show economic headroom in this bounded sample; the tested
previous-score policy loses badly. A practical way to avoid long convergence
sequences is therefore the unresolved issue exposed by these data. This report
does not choose another driver, reopen TT/history policy, recommend production
adoption, or decide whether SR-004 should continue or close. Those decisions
