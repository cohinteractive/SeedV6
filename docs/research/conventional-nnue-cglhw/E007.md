# E007 — Conventional material output buckets

Prospective implementation plan, 2026-10-22. Broader BT4 data improved held-out
fit, but E006's production screen remains weak and MSE is flat from64 to128.
E006's predeclared lower-rate stage remains a separate active experiment.

The next conventional capacity refinement is eight material-count output heads
with the existing 256-unit, dual-perspective, 10 mirrored king-bucket SCReLU input.
This follows the pinned Bullet progression example's MaterialCount<8> design.
It lets output weights vary with game phase while retaining one head evaluation
per position. Bucket=(piece_count-2)/4 for valid2..32-piece positions. The selected
head must change correctly after captures; promotion changes piece type but not
piece count. No search-policy change or production-default replacement is included.

Preserve S6CNU001 compatibility and all frozen checkpoints. Give the new geometry
an explicit versioned identity and reject mismatched geometry/checksums. Keep long
output arithmetic and independent full-rebuild/reference checks. Extend trainer,
export/verification and controlled resume recipes to distinguish1 versus8 outputs.
Old immutable experiments use their frozen trainer binaries if the current build
changes. Do not mutate the active E006 trainer or runtime jars until it finishes.

Verify bucket boundaries and capture/promotion/null/sibling transitions, old-format
behavior, independent arithmetic, native export/GPU parity, UCI and runtime cost.
Use the same verified E006 BT4 dataset/holdout and a separately frozen recipe for
the new candidate. New head geometry requires a distinct training initialization;
any cold start or weight transfer must be explicit, never claimed as exact resume
of the one-head optimizer. Freeze that decision before GPU training. All historical
artifacts remain intact. Strength screens and independent confirmation retain the
existing gates; this architecture is a justified hypothesis, not an accepted winner.
