# M002: bounded exact output-head optimization

Prospective decision22 October2026 after E003 completed. Three development screens
have not established competitive NNUE. E003's incremental evaluation costs about
1.2us versus Pair-2's about90ns on the fixed walk. Do not launch another data growth
trial automatically. Test one local arithmetic optimization, retaining it only if
correctness and measured benefit support it. No weight, schema, search-policy or
production-default changes; no GPU retraining.

At network load, bound the output dot product by
`255 * 255 * sum(abs(head_weight))` in long arithmetic. If at most Integer.MAX_VALUE,
all products, partial sums and paired additions fit int; a separate int kernel can
avoid long arithmetic in the hot loop. Otherwise retain the original long kernel.
The independent unit-major full-rebuild oracle and final long scaling stay unchanged.
E003's bound is612,470,475. This is not permission to assume every network is safe.

Verify focused Java tests including signed-short extremes and bounds immediately
below/above int capacity, randomized clipping inputs and independent arithmetic;
run existing legal/special-move, accumulator/search ownership and fallback tests.
Check frozen E003 cross-language probes again, actual one-/two-worker UCI and exact
before/after scores on its diagnostic cohort. Benchmark unchanged walk/weights with
the same Java flags and no concurrent expensive process. Preserve negative results.
If cost does not improve materially, remove the optimization and retain evidence.
If retained, use a coherent runtime commit with build+1 under root AGENTS.md.

This is an implementation/correctness/cost unit, not a competitive-strength claim.
A faster kernel alone cannot establish C. Determine the next decision from measured
cost and the three weak screens; no unrestricted optimization or training sweep.

The prototype passed24 focused tests but did not improve cost. Its patch and raw
benchmark are preserved; restore the original long kernel and retain the independent
arithmetic boundary regression test. No application build increment for a rejected
runtime prototype. Restored-kernel checks precede final bookkeeping.

Before another empirical commitment, use the existing unpruned and Policy4 factory
controls to diagnose search cost on the same eight frozen development roots. One
worker,32MiB cold TT per root, iterative depths1..4,1s/250000-node bound per root;
one unreported depth3 warm-up round, two measured rounds with rotated mode order.
Compare E003/unpruned, Gen32/unpruned, Gen32/Policy4. No search implementation or
policy change. Different evaluators still produce different trees; only the two
Gen32 modes isolate the policy variable. No Elo or pure arithmetic-speed inference.
This small diagnostic determines whether another NNUE data expansion is justified.

around int capacity/signed extremes) and15 standalone UCI tests, zero failures.
Its incremental benchmark1.218..1.263us did not improve original1.179..1.207us.

benchmark identity. Restored long kernel re-passed24 tests, and measured
1.172..1.223us, zero hot allocations. Application runtime source is unchanged.
Independent arithmetic regression coverage remains useful and is retained.

at depth4 without budget truncation. Both repetitions match nodes/scores exactly.

This is limited diagnostic evidence, never Elo. See m002-search-cost.json.
