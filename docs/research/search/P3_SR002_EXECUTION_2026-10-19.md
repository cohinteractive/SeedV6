## Bootstrap challenge and hypotheses

The old research `FlatExactSearch` is a static-leaf, non-MDP HCE comparison. It
does not implement the current integrated selective tree, completed hints or root
coordination. Its preserved negative result is not a Phase 3 decision. The current
`ExactSearch` has reusable primitive board/move/PV storage already; eliminating
Java recursion does not automatically remove per-node heap allocation.

Main traversal has independent original windows, reduction/nominal/full retries,
selective epochs, completion/hint/history effects and root-job restrictions.
Qsearch is a smaller integrated flattening boundary that retains all main-search
and coordinator behavior. First measure current whole requests, then test a
primitive explicit qsearch stack if justified. This is **partial flattening**;
it cannot establish equivalence or performance for a fully flattened engine.

Hypotheses: (H1) qsearch recursion/frame cost materially affects whole-request cost;
(H2) explicit primitive frames can preserve deterministic Policy 4 execution;
(H3) full flattening has sufficient additional decision value to justify its retry
and maintenance costs. Challenge H3 after measured H1/H2 evidence, without treating
a failed partial prototype as proof that full flattening is inferior.

## Architecture and implementation scope

The full candidate uses 11 integer and four long main-frame arrays, plus six
integer q-frame arrays: 100 bytes/real-ply payload, **25,600 bytes per worker** at
256 slots, plus array headers. Allocation happens only on explicit opt-in.
Existing board/move/PV/evaluator/history state remains worker-local and reused;
the coherent TT and immutable evaluator definitions retain current sharing.
Both main and q traversal are loops; main-to-q is a bounded nonrecursive boundary.
Reduced scouts retain the real child push through nominal verification and full
retry, restore each invocation's own original window, and retain conservative
selective epochs. Shared helpers still own ordering, learning, proof/hint storage,
mate normalization and root effort. Whole-root coordination is unchanged.

The prototype duplicates the traversal skeleton only inside the shared core and
has explicit configuration guards. It does not clone the evaluator, TT, board,
driver, coordinator or independent oracles. It is not a generic replacement for
every historical experimental policy. The recursive path retains all old controls;
HCE/NNUE/other BRN production factories still select their established behavior.
This bounded implementation avoids a broad preparatory rewrite, but maintaining
two feature-rich production kernels would be unacceptable future engineering cost.
Any later accepted construction must extend its selected kernel coherently while
retaining required independent references and intentional comparison controls.

**1.0367 [1.0227,1.0525]**, aggregate CPU ratio **1.0429**, 61/117 ms of compilation,

short-request cost. Its boundary-crossing interval and first-run adverse result
remain limitations; they are not pooled with confirmation or erased by follow-up.
The per-pair short-request CPU geometric estimate is unreliable at the coarse
counter tick resolution (10 of 240 pairs have nonpositive CPU in at least one arm
and cannot enter log ratios); its raw
12.4% statistic remains in the summary, while 4.3% is the descriptive ratio of
aggregate CPU. Neither supplies precise short-request CPU equivalence.

Separate JFR/JIT/NMT runs exercised recursive and full-flat owners individually at
one/four workers. Both reach C2. Recursive main bytecode is 7886 bytes versus 2529
for the restricted flat main, yet the final observed compiled nmethod sizes are
68,768-70,312 bytes versus 99,720-105,272 bytes respectively (nmethod size
includes metadata, not only instructions). Flattening does not automatically
improve inlining or code locality. Flat main has more observed C2 versions (7/8
versus 3/4) and later final compilation observations (10.097/7.641 s versus
2.290/2.397 s). These are observed compilations in the profiles, not stable universal
warmup durations. Move generation, board transitions, SEE, history and traversal
remain visible costs. Sampling cannot causally isolate Java call overhead.

Corrected profile summaries are `profile-*-v2-summary.json`. Original v1 summaries
used `jfr print`'s default five-frame display depth, limiting their sampled-stack
counts; they and their raw output are preserved. The v2 extraction explicitly
prints up to 256 frames from the same immutable recordings. It finds up to 27/32
main/q method frames in recursive runs (including inlined scopes) and zero such
recursive-method frames in the full-flat runs, with no truncated sampled
Search traces. Driver diagnostics observed maximum real ply 35 and qply 29 in
confirmation. This demonstrates eliminated Search recursion within the sample,
not maximum possible native-stack high-water measurement.

Median scoped one-worker allocated bytes/request were **85,028/85,120**, about
0.0865 bytes/admitted node for both. Four-worker medians were
**1,772,544/1,770,584**, about 1.76 bytes/node, including coordination/result objects.
No recurring frame-object allocation was introduced. One-worker measured GC count
was zero for both; four-worker counts were 1/7, despite nearly identical allocation.
GC event placement and background JIT vary within the shared JVM, so that count
alone does not establish a candidate allocation regression. The separate warmed
short diagnostic also has a GC imbalance (1/5), which remains visible.

All isolated profile heaps committed 256 MiB with 768 MiB reserved. Four-worker
whole-process thread stack reservations were the same 16 MiB, with approximately
803/807 kB committed at exit; helper pools had drained/closed. Single-worker
reservations differed by one JVM thread (17/16 MiB), which is not a Search memory
saving. NMT is whole-process exit state, not peak Search memory. The only fixed
Search frame delta is the explicit 25,600-byte payload per worker plus headers.
No material allocation/GC or reserved-stack advantage is demonstrated.

Hardware branch/cache-miss counters, exact native-stack high-water usage, other
JDKs/platforms and exhaustive worker/resource domains were not measured. Primitive
frame layout and direct helper reuse are observed implementation facts, not cache
locality proof. Profiling timings are not clean confirmation observations.
